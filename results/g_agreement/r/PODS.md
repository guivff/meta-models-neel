## Rule for every session and every pod (Guiv, 2026-10-19 17:16Z; applies to all streams, not only this runbook)

**Any pod you start or resume must have both guards (1, 2) armed before your first command on it, and every session must follow 3 and 4 to reach it, 5 before any full run, 6 before any resume or create, 7/7b before any stop or idle hold, 8 when EUR-IS-3 has no GPU, and 9 for every stop credential:**
1. **A self-stop** (as amended 2026-10-19 19:36Z, below). The self-stop is an **explicit final step** of the job chain. It calls
   the stop **by the pod's explicit id** (`.env`'s `RUNPOD_POD_ID` may name another pod), and only **after the outputs are safely
   pulled to the Mac or written to the volume**. **Never an EXIT trap.** The chain runs **detached from SSH**
   (`setsid nohup bash <chain> …`), so a closing SSH session cannot end it. **Failures are covered by the hard stop and the
   watchdog**: a chain that dies early leaves its pid dead, so the watchdog stops the pod after 15 min, and the hard timeout
   caps a job that hangs. The hard timeout is still required. This applies to short resumes too: a "10-minute" pull from a
   stopped pod needs both.

2. **An idle watchdog** (as amended 2026-10-19 17:31Z, below). A background loop on the pod that stops it, by its own id, after
   **15 consecutive minutes at 0% GPU utilisation** (`nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader,nounits`,
   sampled every ≤ 60 s), **unless the job process is alive AND one of its output files grew in the last 5 minutes**. In that
   case it logs `idle but productive` on every sample and keeps the pod up, but **never beyond 45 consecutive minutes at 0% GPU,
   when it stops the pod regardless**. "Job process" means the PID the job chain records at launch; "output files" means the
   paths the job declares at launch (size or mtime increase). Any sample above 0% resets both counters. The watchdog runs from
   the first minute, independently of the job, so it also catches a job that never starts: a resumed pod with no job, or a hung
   job, has no live process with growing output and still stops at 15 min.
3. **The pod's own SSH address** (Guiv, 2026-10-19 17:45Z). Wait until the pod's **own** API entry (the single-pod query by its
   id) shows its SSH address. Never parse it from a shared list such as `myself { pods }`: right after a resume a pod's runtime is
   null, so a grep over the list runs on into the next pod's ports (17:29Z, text arm v2 → P8, Known gaps below).
4. **The first SSH command checks the id** (Guiv, 2026-10-19 17:45Z). It reads the pod's id from the pod itself
   (`cat /proc/1/environ | tr '\0' '\n' | grep RUNPOD_POD_ID`, i.e. the container's `$RUNPOD_POD_ID`, or the API looked up by
   the pod's IP) and **aborts if it doesn't match the intended id**, before any guard, rsync or job runs.
5. **Smoke before every full run; runners in durable places; no stopping traps** (Guiv, 2026-10-19 19:38Z).
   - **Smoke run that asserts coverage.** Before any full run, a smoke run must **assert that every pre-registered arm and
     condition produced at least one row**: each arm × condition (× render / layer / site where the pre-registration
     names them) present in the output with ≥ 1 row. If any cell is empty it must **fail loudly**: non-zero exit, a
     `SMOKE FAILED: missing <arm/condition>` line in the log, and no full run launched. A smoke run that only checks the
     process exited 0 does not count.
     *Why, in one case (WS4 SWAP, 2026-10-19):* readers were bound with `steer.bind_readers`, whose J-lens defaults to R5's
     layers [38, 42]. SWAP edits 24–44 step 4, so **both J-lens arms produced zero rows while the control arms ran normally**:
     a run that would have completed, reported healthy row counts, and silently omitted half the experiment. The CPU mock
     missed it, because it binds the lens at every mock layer; the foreground smoke on the pod caught it. A helper whose
     defaults encode one experiment's geometry is dangerous when another reuses it.
     *Caught by the smoke (panel, rp27 Q27, 2026-10-19 ≈ 22:0xZ):* `SMOKE FAILED: phase P crashed`. The position-probe workers
     re-activated the pair only when its config had a `pos_probe` key, so Q27 (and Q32, later that night) looked up Gemma's
     `rg/states_pos` path. No full run was launched. The fix (`6fe7807`, with a regression test) re-activates every pair in its
     workers; it was synced to P32 before its phase P, and Q27 was relaunched on the same pod at 22:06Z under the same guards.
     After the fix: `SMOKE PASSED: 92/92 arm × condition cells have rows` (gate: sst2 AO primary at chat, AUROC 0.939). Q27 froze its
     manifest, and the full run started at ≈ 22:30Z.
     *SWAP instance (Guiv, 21:57Z; WS4 `db6cfaa`):* `swap.py --phase audit` compares the saved read-back states against the steer rows
     per cell (part × layer × arm). It needs exactly one state per row key, no orphan states, and consistent .npy/.json pairs, and
     prints `SMOKE FAILED: <cell> missing <n> states (<keys>)` and exits non-zero otherwise. It reads files only, no GPU. It runs after
     phase A and after score/B in `ws4_swap_resume.sh`, before the final stop; a failure sets the chain's exit code and the stop still
     happens. It catches what a row count cannot: on 2026-10-19 the rows were complete while 22 L24 states were lost to a resume bug.
     *Reference implementation:* the panel's `projects/r_panel/smoke_assert.py`. It checks every BRIEF_RP arm × condition
     and prints `SMOKE FAILED: missing <cell>` with exit 1 (pending push).
   - **Runner scripts live on the volume or in the repo, never in `/tmp`.** `/tmp` and the container disk are wiped when
     the pod stops, so a runner kept there leaves no record of what ran, and a resume cannot rerun it. Put chain scripts,
     guard scripts and their logs under `/workspace/<stream>/…` (the volume) or commit them to the repo. On a pod with no
     volume, pull them to the Mac with the outputs.
   - **No exit traps that stop the pod** (see item 1, amended 19:36Z). The stop is an explicit final step after the outputs
     are safe; failures are covered by the hard stop and the watchdog.
